# Stage Z: inventory architecture audit and accepted baseline

Prepared **2026-10-26**. **Stage Y, including its ground/connection/density refinement, is accepted by the director.** Stage Z is limited to repository inspection, baseline validation and the [architecture proposal](../plans/phase_7_stage_z_hybrid_inventory_plan.md). No inventory implementation, asset generation or save migration has begun. The [director ledger](../ledgers/phase_7_stage_z_hybrid_inventory.md) is an unchanged copy of the supplied attachment.

## Verified current architecture

Normal startup is `project.godot` → `scenes/levels/asset_recovery_arena.tscn` → `mission_arena.gd`, which extends `raider_arena.gd`. The expanded mission is explicitly launched as `scenes/levels/expanded_salvage_complex.tscn`, with `expanded_asset_recovery.tres`. Both normal configurations use three finite stock points, machine components, five scheduled Raiders, two bounded response tickets, personality/social policies, Recall and post-death following. Neither has a hybrid inventory feature flag or a preparation inventory.

In objective missions, the arena disables simulation before Deploy while the overlay remains active. Encounter layout resolution places stock and chooses profiles before `RaiderArena._ready()` builds the material ledger. The base arena then creates flare/equipment, Recall/stash, navigation, machines, social relationships, objectives and observers. Raiders arrive after navigation is ready and deployment has started. This initialization order is an integration seam: a shared item authority must exist before either ledger, machine stock or actor loadout is initialized.

The editor and **all 41 suites passed**, with every completion marker checked. **32 accelerated suites** reported only the previously recorded shutdown retention of `AudioStreamWAV` / `AudioStreamPlaybackWAV`; verbose logs found no other leaked object type. These are passing assertions with retained warnings, not clean accelerated shutdowns.

The existing 40-second autonomous replay for seeds **87017 / 87018** exactly matches the accepted Y refinement replay, including geometry/navigation, actor timeline, shots, transfers, counters/events, equipment, objectives and stash. This is a bounded baseline, not a complete 180-second play-test. The Forward+ physical fire → death → recovery → Recall banking → restart → player death/follow-cycle check passed without warnings/errors.

All **345 pinned files** under scripts/resources/scenes/tests/tools plus project/bus/environment-manifest inputs remain byte-identical after inspection and validation. The Y evidence already supplies normal-view rendering cost; no new inventory performance or functional behavior is claimed.

## Findings driving the proposal

1. Retain the material and equipment APIs as compatibility projections over **one** underlying item owner/transfer engine. Merely attaching item dictionaries to the existing independent counters would create duplicate authority.
2. Migrate version-1 balances into actual stacks/equipment once. Receipt history remains history, not an additional source of inventory. The old append-only save invariant cannot validate loadout debits.
3. Persist a deployment escrow/debit before actors start. Add durable settlement identity before banking or forfeiture becomes final; explicitly handle crash, restart, stale backup and write-failure paths.
4. Adapt the existing scalar AI goal/loot queries to capacity and carried-loot value. Preserve the accepted FSM, perception, relationships, commitment, physical firing and timings.
5. Introduce real equipment ownership without silently changing stats. The first functional integration can bind the existing player blaster/initial Raider rifle and make unsupported upgrade slots explicit data foundations.
6. Treat direct player scavenging, Raider equipment/container looting, loadout risk, inventory input suppression and capacity limits as proposed gameplay changes requiring this Stage Z architecture approval.
